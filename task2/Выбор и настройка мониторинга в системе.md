### Мотивация

Внедрение мониторинга необходимо для:
- **Контроля состояния системы** в реальном времени, особенно после открытия API, когда нагрузка непредсказуема.
- **Выявления узких мест** – медленных запросов, высокого потребления ресурсов, проблем с БД.
- **Предотвращения инцидентов** – раннее обнаружение аномалий (рост числа ошибок, заполнение диска) позволяет реагировать до жалоб клиентов.
- **Сбора данных для планирования мощностей** – понимание трендов нагрузки помогает вовремя масштабироваться.
- **Улучшения качества обслуживания** – метрики доступности и времени ответа стимулируют команду к оптимизации.

Бизнес-ценность: снижение числа просроченных заказов, повышение удовлетворённости клиентов (B2C и B2B), уменьшение времени на диагностику проблем, возможность давать гарантии SLA партнёрам.

### Выбор подхода к мониторингу

Для разных частей системы применимы разные подходы:

- **Для API-сервисов (Shop API, CRM API, MES API)** – подход **RED** (Rate, Errors, Duration): количество запросов в секунду, доля ошибок, время ответа. Это даёт картину здоровья сервисов с точки зрения пользователей.
- **Для инфраструктурных компонентов (БД, RabbitMQ, S3)** – подход **USE** (Utilization, Saturation, Errors): загрузка CPU/памяти, количество соединений, размер очередей, ошибки ввода-вывода. Позволяет выявить насыщение ресурсов.
- **Для бизнес-процессов** – «Четыре золотых сигнала» (латентность, трафик, ошибки, насыщение) дополняются специфическими метриками, например, количество заказов в каждом статусе, время нахождения в статусе.

### Метрики для отслеживания

**RabbitMQ**
- Number of dead-letter-exchange letters – для контроля потерь сообщений (ярлыки: очередь, причина).
- Number of messages in flight – показывает текущую нагрузку на очередь (ярлыки: очередь).

**API-сервисы**
- Number of requests (RPS) для каждого API – общая нагрузка.
- Number of requests per user – для выявления аномалий (например, один пользователь генерирует слишком много запросов) – ярлыки: user_id.
- Response time (latency) – перцентили (p50, p95, p99) для оценки производительности.
- Number of HTTP 200 и HTTP 500 – мониторинг ошибок (ярлыки: endpoint, метод).
- Number of simultaneous sessions – для оценки параллельной нагрузки.

**Ресурсы серверов (CPU, Memory)**
- CPU % для каждого API – загрузка процессора (ярлыки: инстанс).
- Memory Utilisation – утилизация памяти.
- Memory Utilisation для БД – аналогично.

**Базы данных**
- Number of connections – количество подключений (ярлыки: БД).
- Size of shop db instance / MES db instance – для планирования.

**S3**
- Size of S3 storage – контроль объёма хранилища 3D-файлов.

**Дополнительные метрики** (не в списке, но важны):
- Количество заказов в каждом статусе (бизнес-метрика).
- Время между статусами (например, от SUBMITTED до PRICE_CALCULATED).
- Количество активных операторов и взятых ими заказов.

### План действий

1. **Выбор стека мониторинга** – Prometheus для сбора метрик, Grafana для визуализации, Alertmanager для оповещений.
2. **Установка и настройка экспортеров**:
   - Node Exporter на каждом EC2 для метрик ОС.
   - Exporter для PostgreSQL (например, postgres_exporter).
   - Exporter для RabbitMQ (rabbitmq_exporter).
   - Для Spring Boot приложений – Micrometer с поддержкой Prometheus.
   - Для C# – аналогично (App Metrics или Prometheus-net).
3. **Инструментирование кода** – добавление метрик в сервисы (RPS, latency, ошибки, счётчики заказов).
4. **Настройка дашбордов в Grafana** для каждой группы пользователей (операторы, разработчики, бизнес).
5. **Определение порогов насыщения и настройка алертов** (см. доп. задание).
6. **Обучение команды** работе с мониторингом.

### Дополнительное задание: показатели насыщенности

Пороговые значения:
- **CPU % для API-сервисов** – >80% в течение 5 минут → предупреждение (возможно, нужно масштабирование).
- **Memory Utilisation** – >90% в течение 10 минут → предупреждение (риск OOM).
- **Number of connections для БД** – >80% от максимального значения (например, max_connections = 100, порог 80) → предупреждение.
- **Размер очереди RabbitMQ** – >1000 сообщений в очереди → предупреждение (накопление).
- **Response time (p95)** для критических эндпоинтов – > 3 секунд →  предупреждение.
- **Количество HTTP 5xx** – >1% от общего числа запросов за 5 минут → предупреждение.

При превышении порогов:
- Автоматическое создание тикета в Jira.
- Отправка уведомления в Slack команде.
- В критических случаях (например, падение доступности) – звонок дежурному (через PagerDuty или аналоги).
- Если настроено автомасштабирование – запуск дополнительного инстанса (для stateless сервисов).
