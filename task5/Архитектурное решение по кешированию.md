### Мотивация

Проблема: медленная загрузка страницы со списком заказов в MES. Операторы сортируют заказы по новизне, и страница грузится долго из-за сложных запросов к БД. Внедрение кеширования позволит:
- Уменьшить время отклика для операторов.
- Снизить нагрузку на БД MES.
- Улучшить пользовательский опыт, что важно для вознаграждения операторов.

Планируется кешировать список заказов с учётом фильтров (статусы, сортировка по дате). Поскольку заказы добавляются и меняют статусы часто, кеш должен быстро инвалидироваться.

### Предлагаемое решение

Выбираем **серверное кеширование** с использованием Redis. Причина: клиентское кеширование (например, на фронте) не решит проблему, т.к. данные динамические и каждый оператор видит актуальные заказы.

Паттерн: **Cache-Aside** (Lazy Loading). При запросе списка заказов приложение сначала проверяет кеш. Если данных нет, выполняет запрос к БД, сохраняет результат в кеш и возвращает. При обновлении статуса или создании заказа данные в кеше инвалидируются (удаляются) или обновляются (Write-Through). Почему Cache-Aside? Он прост, подходит для частого чтения и редкой записи. Write-Through потребовал бы синхронного обновления кеша при каждой записи, что может замедлить операции. Refresh-Ahead сложнее и требует прогнозирования.

**Диаграмма последовательности**:

```
Оператор -> MES Frontend: Запрос списка заказов
MES Frontend -> MES API: GET /orders?status=...
MES API -> Redis: Запрос ключа "orders:status:..."
Redis --> MES API: Нет данных
MES API -> MES DB: SELECT ... WHERE status=...
MES DB --> MES API: Результат
MES API -> Redis: SET "orders:status:..." результат
MES API --> MES Frontend: Список заказов
...
Оператор -> MES Frontend: Взять заказ (смена статуса)
MES Frontend -> MES API: PATCH /orders/{id} (status=MANUFACTURING_STARTED)
MES API -> MES DB: UPDATE ...
MES DB --> MES API: OK
MES API -> Redis: DEL "orders:status:..." (инвалидация кеша)
MES API --> MES Frontend: Успех
```

**Стратегия инвалидации**: инвалидация по ключу при изменении данных, влияющих на список. При изменении статуса заказа удаляются все ключи, которые могли включать этот заказ (например, все ключи по статусам, так как заказ переходит из одного статуса в другой). Можно также обновлять конкретный ключ, если известно, что заказ был только в одном статусе, но проще удалять. Временная инвалидация (TTL) тоже нужна, чтобы избежать застоя данных (например, TTL = 5 минут).

Сравнение стратегий:

| Стратегия | Описание | Плюсы | Минусы |
|-----------|----------|-------|--------|
| Cache-Aside с удалением | При чтении – запрос, при изменении – удаление ключей | Простота, актуальность данных | Может быть много удалений при частых изменениях |
| Write-Through | При записи обновляем кеш | Кеш всегда актуален, чтение без промахов | Замедление записи, сложность обновления агрегированных списков |
| Refresh-Ahead | Асинхронное обновление кеша перед истечением | Снижение задержек при чтении | Сложность реализации, возможна устаревшая информация |

Выбираем Cache-Aside с удалением как наиболее подходящий для данного сценария: записи (изменение статусов) случаются часто, но не настолько, чтобы нагружать Redis лишними удалениями, а простота важна.

### Дополнительное задание: два варианта решения

**Вариант 1: Кеширование на уровне API с Redis (описан выше).**

**Вариант 2: Использование материализованных представлений в БД и индексов** (без внешнего кеша). Оптимизация запросов, добавление индексов по статусу и дате, возможно, денормализация (например, отдельная таблица для дашборда с предрассчитанными данными). Это тоже своего рода кеш, но на стороне БД.

Сравнение:

| Критерий | Вариант 1 (Redis) | Вариант 2 (оптимизация БД) |
|----------|--------------------|-----------------------------|
| Производительность | Очень высокая (in-memory) | Высокая, но зависит от индексов |
| Нагрузка на БД | Снижается значительно | Не снижается (запросы всё равно идут) |
| Сложность реализации | Средняя (нужен Redis, настройка инвалидации) | Низкая (индексы) или средняя (денормализация) |
| Актуальность данных | При правильной инвалидации – высокая | Всегда актуальна |
| Масштабирование | Легко | Ограничено БД |

**Заключение**: Вариант 1 предпочтительнее, так как он не только ускоряет ответ, но и снимает нагрузку с БД, что важно при росте числа заказов. Вариант 2 может быть временным решением, но не решит проблему пиковых нагрузок. Поэтому выбираем Redis с паттерном Cache-Aside.
